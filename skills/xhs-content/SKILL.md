# 小红书图文与动画内容 Skill

## 适用场景

当用户提供现成文字，要求改成小红书 Emoji 风格文案，或给出网页链接、文章主题、产品信息，要求生成文案、配图、动画、可复制内容、保存草稿或上传发布时使用本 Skill。全程使用简体中文交流，提问、说明和交付文案也使用简体中文。只有现成文字且仅要求改写时，直接按下方“纯文字改写”处理，不启动素材生成、归档或发布流程。用户只发送链接或主题、没有指定内容形态时，先根据来源特征推荐“图文”或“动画”，询问用户选择后再提取完整素材。用户同时没有指定交付方式时，再询问保存本地还是上传并保存草稿。没有来源链接且缺少可改写文字时，先向用户索要主题、受众和必要事实；若信息足够，也可以根据主题直接创作，但要标明创作性内容。

## 纯文字改写

- 保留原文的事实、观点、语气强弱和结论；只调整标题、段落、措辞和 Emoji，不补充未经原文支持的数字、效果或承诺。
- 输出吸引人且准确的标题，每个正文段落至少放一个与内容相关的 Emoji，末尾添加与原文主题相关的话题标签；不要为了凑标签引入原文没有的新主题。
- 改写前后核对关键信息是否一致，检查每个正文段落的 Emoji 和末尾标签。仅要求改写时直接返回成品文案，不要求选择图文或动画，也不创建素材目录。
- 用户提供的是 `xxx`、省略号等占位内容时，不猜测主题或编造正文；用简体中文请用户补充实际原文。

## 内容形态决策

在用户确认前只做轻量判断，不生成图片、视频或发布草稿：

1. **推荐图文**：来源主要是产品功能、文章要点、清单、对比、截图或静态界面。图文更容易保留事实证据，制作和发布核验成本较低。
2. **推荐动画**：来源主要是交互演示、操作步骤、时间线、数据变化、空间关系、粒子或三维过程，或者核心价值依赖节奏和连续动作。动画能更清楚地呈现变化，但需要逐帧渲染、声音和视觉复核。
3. **无法判断时推荐图文**：明确说明原因，并允许用户改选动画。

提问应明确给出推荐和理由，例如：

```text
我判断这个链接以产品界面和功能清单为主，推荐做图文，方便保留页面证据和关键信息。你想做图文还是动画？另外请选择：保存本地素材，还是上传到小红书并保存为草稿？
```

用户选择动画后，按任务读取以下已安装技能：

- `skills/stick-scene/SKILL.md`：火柴人场景，用于讲解分析视频中的流程、协作关系、产品原理与因果过程；配合时间线、字幕、旁白和导出流程形成完整视频，预览、采帧与检查使用 ego-browser。
- `skills/claude-motion-design/skill/motion-design/SKILL.md`：HTML + Playwright + FFmpeg 逐帧渲染，适合产品发布和功能演示。
- `skills/claude-motion/.claude/skills/motion-design/SKILL.md`：Remotion 动效节奏、时间线和视觉规则。
- `skills/claude-motion/.claude/skills/review-loop/SKILL.md`：渲染草稿、逐帧截图、自检和返工。
- `skills/claude-motion/.claude/skills/sound-design/SKILL.md`：音效编排、混音和响度核验。
- `skills/claude-motion/.claude/skills/web-sims/SKILL.md`：粒子、三维对象和模拟类视频。

动画完成条件：必须有实际视频文件，或在 `manifest.json` 中明确标记 `videoStatus: "pending"` 并保存可执行的渲染计划；不能用静态截图、代码或点击过保存按钮代替视频完成证明。

## 工具与访问边界

- 所有网页打开、导航、点击、填写、截图和页面内容提取都必须使用 **ego-lite 的 `ego-browser`**（先运行 `ego-browser skill`，再通过 `ego-browser nodejs` 操作）。禁止改用 Playwright、内置浏览器、CDP 直连或其他浏览器自动化工具。
- 需要联网检索或读取动态网页时，遵循 `web-access` Skill；先确认页面内容已经加载，再提取正文和图片信息。
- 生成位图时优先使用 `imagegen` Skill。若无法调用图像生成，保存可执行的图片提示词，并明确说明尚未生成图片。
- 小红书创作者平台入口：`https://creator.xiaohongshu.com/publish/publish?source=official&from=menu`。
- 不能绕过登录、验证码、风控或平台权限。页面阻塞时保存已获得的素材并报告阻塞点。
- 不提供绕过、隐藏或对抗平台审核的方法；只做真实、清晰、可追溯的内容整理，并通过发布前合规预检降低误判和违规风险。

## 工作流程

### 1. 读取和核验来源

1. 对每个 URL 记录最终 URL、页面标题、作者、发布时间（如可见）和来源站点。
2. 提取文章主旨、关键事实、可引用数据、原文图片及其说明；不要只依赖搜索摘要。
3. 将信息分成“来源事实”“合理概括”“创作性表达”三类。来源没有支持的数字、功效、承诺和因果关系不得写成事实。
4. 图片属于来源站点时记录原始地址和使用限制；不确定版权时不直接搬运，改用原创配图提示词。
5. 给出网址时必须使用 `ego-browser` 打开该网址，并从已核验页面中选择至少一个最能体现产品特色的区域截图（优先首屏产品演示、核心功能区或真实结果展示）。截图必须来自实际页面，不得用流程图替代；记录截图对应的 URL、页面区域、截取时间和版权备注。
6. 提取项目或产品的正式名称、短地址（优先域名 + 项目路径）和页面标题，供图片署名与文案核对使用；名称、地址不得凭空补写。

### 2. 生成小红书文案

输出一份可直接复制的文案，结构固定为：

```text
标题：……

正文：
……😊

……✨

话题：#话题一 #话题二 #话题三
```

- 标题要有明确主题和阅读收益，避免夸大、虚假稀缺和绝对化表述；生成后检查创作者平台当前显示的长度限制。
- 每个正文段落至少有一个与语义相关的 Emoji，Emoji 不要连续堆砌。
- 保持原文核心意思；可重排结构、压缩长句、补充过渡，但不能擅自改变结论。
- 末尾追加 3-8 个相关标签，标签应覆盖主题、场景和受众，避免无关热门词。
- 除非用户要求，不在成品正文中加入“据 AI”“以下由模型生成”等实现细节。

### 3. 生成和整理图片

- 默认生成 1 张封面、1 张真实网页特色截图和 1-3 张原创正文图；图文主题、色调、文字和正文保持一致。真实网页截图是必选素材，流程图只能作为补充，不能占据全部图片。
- 网页截图保存为 `source-feature.png`，保留原始页面视觉和必要的产品文字；不得擅自裁掉能改变语义的内容。若页面含隐私、登录信息、用户头像或不适合公开的内容，改截公开区域或打码后再使用。
- 项目身份标识是必选项：至少一张可发布图片（封面优先，或第一张正文图）必须在清晰、高对比、非极小字号的区域写出“项目名 + 短地址”，例如 `项目：learn-from-materials · github.com/dmoshehun-prog/learn-from-materials`。不得把地址藏在与背景同色、透明度过低、图片边缘或平台裁切高风险区域。
- `source-feature.png` 可以采用“原始截图 + 截图外部署名带”的构图：截图内容保持原样，在截图下方或旁边增加一块明确标注 `来源：项目名 · 短地址` 的署名区域。署名带不能覆盖、篡改或伪造网页原文；在 `source.json` 和 `manifest.json` 记录署名位置。
- 默认画布使用竖版 3:4（例如 1080x1440）；涉及信息卡片时优先保证中文清晰、留白充足、对比度足够。
- 图片中的中文文字应尽量少。需要长段文字时，把文字放入 `copy.md`，不要依赖图片内小字传达关键信息。
- 不复刻受版权保护的 Logo、人物肖像或原图；需要引用时保留来源并改用原创视觉方案。
- 截图属于来源页面内容时，不得把截图中的宣传语、数据或视觉效果改写成未经核验的事实；`source.json` 中同时记录截图 URL、页面区域和版权归属。若无法确认截图使用限制，保留截图作为来源证据但不要把它作为可发布图片，并在 `manifest.json` 标记 `sourceScreenshotStatus: "reference_only"`。

#### 图片与文案合规预检

生成和上传前逐项检查，并把结果写入 `manifest.json` 的 `complianceChecks`：

- 项目名和短地址在至少一张可发布图中清晰可读，且与 `source.json` 的核验值一致。
- 没有把“开源”“MIT”“官方”“第一”“最强”等未经页面支持的表述写成事实；许可证只在来源页面明确可见时使用。
- 没有虚构功能、效果、用户数量、收益、排名、发布时间或成功案例；推测和创作性表达已单独标记。
- 没有使用冒充官方、诱导点击、虚假稀缺、保证收益、医疗或金融绝对承诺、恶意攻击或其他高风险营销表述。
- 没有未经授权搬运 Logo、人物肖像、原图或受版权保护的大段文字；来源截图已标记用途和版权状态。
- 没有隐藏文字、透明水印、重复关键词、批量灌水、伪造互动或其他试图影响审核结果的手段。
- 标题、正文、话题和图片中的项目名、地址、数字相互一致，未出现平台提示的截断或敏感词误用。

如果预检未通过，先修正文案或图片并记录原因；不要以改写、遮挡或编码的方式规避平台检测。平台最终审核结果不可由本 Skill 保证。

### 4. 按日期和编号归档

在项目根目录的 `history/` 下创建以下结构，日期按 Asia/Shanghai 计算；`history/` 由 Git 忽略，仅保存在本地：

```text
history/
└── YYYY-MM-DD/
    └── 001/
        ├── cover.png
        ├── source-feature.png
        ├── image-01.png
        ├── image-02.png
        ├── copy.md
        ├── source.json
        └── manifest.json
```

- 在 `history/YYYY-MM-DD/` 中，同一天已有目录时，使用三位数字递增编号（`001`、`002`……），不能覆盖已有素材。
- `copy.md` 只放可复制的标题、正文和标签；`source.json` 保存来源 URL、抓取时间、来源摘要、项目名称、短地址、截图 URL、页面区域和版权备注；`manifest.json` 记录图片文件、尺寸、生成提示词、截图来源、项目身份标识和发布状态，截图字段至少包含 `sourceUrl`、`section`、`capturedAt`、`copyrightNote` 和 `sourceScreenshotStatus`，并记录 `projectIdentity.name`、`projectIdentity.shortUrl`、`projectIdentity.imageFile`、`projectIdentity.placement` 和 `complianceChecks`。
- 生成前后检查文件确实存在；如果图片生成失败，保留 `image-prompts.md`，并在 `manifest.json` 标记 `imageStatus: "pending"`。

### 5. 保存草稿或发布

只有用户明确选择由 Skill 保存草稿或要求发布时才进入创作者平台：

1. 使用 `ego-browser` 打开创作者平台，确认当前账号和登录状态。
2. 上传封面及正文图，填写标题和正文；选择保存草稿时先在编辑器核对图片数量，再执行“暂存离开”并核对草稿箱中的标题，不点击“发布”。
3. 核对图片顺序、标题、正文、标签和平台提示，确认真实网页特色截图位于封面之后且清晰可读；确认至少一张图片中的项目名和短地址未被裁切；发现截断或格式异常先修正本地素材。
4. 只有用户明确要求发布，才在最终“发布”动作前向用户展示将要提交的标题、图片数量和目标账号，并等待用户明确确认；用户已经在同一轮明确说“立即发布”时，可将该指令视为确认。
5. 发布后只在页面显示成功状态或可核验的笔记链接时标记为成功；否则标记为 `publishStatus: "unknown"` 或 `"failed"`，不得凭点击动作推断成功。

## 最终回复格式

简要说明已生成的目录和文件，并直接给出可复制文案；同时列出实际打开的网址、项目名和所截取的特色页面区域，并说明项目名与短地址放在哪张图片的什么位置。本地保存时说明“已生成本地素材，未发布”；保存草稿时说明目标账号、草稿箱核验结果及草稿存储限制；执行发布时附上可核验的发布结果或失败原因。不要把静态文件存在或点击保存误报为平台已发布。
